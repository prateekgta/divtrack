System Overview
All-Java backend. Single PostgreSQL with 3 schemas (auth/portfolio/market). Redis as shared pub/sub bus. Spring Cloud Gateway handles routing, JWT, rate limiting, and WebSocket fan-out.
①Spring Cloud Gateway (:3000) — JWT validation (no network call), rate limiting, proxy, WS fan-out.
②Auth Service (:8081) — only service with RSA private key. Signs JWTs. All others only verify.
③Portfolio Service (:8082) — Holdings CRUD. Reads Redis for live prices (avoids HTTP hop).
④Market Data (:8083) — scrapes Yahoo/Finnhub every 60s. Circuit breaker. Publishes to Redis pub/sub.
⑤Single PostgreSQL — 3 schemas (auth/portfolio/market). Each service has its own Flyway history. No cross-schema joins in code.
⑥Redis — price cache (TTL 90s), prices:live pub/sub, rate limit counters.

Pub/Sub Deep Dive
Pub/Sub = Push model. Publisher fires once. All subscribers receive it. No polling. Think of Java's @EventListener but distributed across processes and pods.

Normal Redis (GET/SET) vs Pub/Sub

GET/SET: You ask, Redis answers. Request/response. One-to-one.

Pub/Sub: Publisher fires, Redis delivers to ALL subscribers simultaneously. Push. One-to-many. Subscriber never polls.

Why not just poll from the browser?

100 users, 9 tickers = 100 × every 5s = 1,200 req/min just for prices. With pub/sub: Market Data publishes 9 messages/60s = 9 req/min. 133× fewer requests.

The code (already written for you)

// Market Data — PricePublisher.java redisTemplate.convertAndSend("prices:live", json); // Gateway — RedisSubscriberConfig.java container.receive(ChannelTopic.of("prices:live")) .map(msg -> msg.getMessage()) .flatMap(json -> fanOutHandler.fanOut(ticker, json)) .retry() // re-subscribe if Redis drops .subscribe();

Challenge: Redis restarts lose subscriptions

If Redis goes down and comes back, the subscription is gone. The .retry() operator automatically re-subscribes. Always add it.

Gateway Internals
Spring Cloud Gateway is reactive (WebFlux) — non-blocking. Every request passes through a filter chain before being proxied.

SCG can proxy WS — but NOT fan-out

SCG can transparently forward ws:// to ONE backend. But for fan-out (1 Redis message → N browser sessions), you need a custom WebSocketHandler. That's PriceFanOutHandler.

The order=-1 trick

Without it, SCG intercepts /ws and tries to proxy it. We register our WebSocketConfig at order=-1 so it runs first. SCG's routes sit at order=1.

@Bean HandlerMapping webSocketHandlerMapping() { SimpleUrlHandlerMapping m = new SimpleUrlHandlerMapping(); m.setUrlMap(Map.of("/ws", handler)); m.setOrder(-1); // before SCG return m; }

Reactive challenge — never block

In WebFlux you cannot call session.send().block(). You must compose Mono/Flux chains. The fan-out uses Flux.fromIterable(sessions).flatMap(...) — non-blocking, concurrent sends.

Stale session cleanup

When a browser tab crashes, no clean WS close is sent. The session stays in SessionRegistry until the next fanOut() call catches the send error and calls registry.deregister(). Lazy but effective at MVP scale.

Free Hosting Stack
AWS is great but expensive after free tier. For 10 users/day, this free stack handles everything and costs $0-5/month vs AWS $40-75/month.

Vercel — Frontend (Free)

Same company as Next.js. Auto-deploys from GitHub on push. Edge CDN. 100GB bandwidth/mo. Zero config for Next.js. Custom domain free.

Railway — Java Services ($5/mo hobby)

Connect GitHub → detects Dockerfiles → one-click deploy. Private networking between services (internal URLs). Env vars in UI. Auto-restarts crashed services. $5/mo covers all 4 services at MVP scale.

# Railway private URLs (no public exposure) AUTH_SERVICE_URL=http://auth-service.railway.internal:8081 PORTFOLIO_SERVICE_URL=http://portfolio.railway.internal:8082

Supabase — PostgreSQL (Free)

500MB, free forever (no 90-day expiry). Built-in PgBouncer connection pooling. Copy the connection string, append ?currentSchema=auth per service. Note: auto-pauses after 7 days of inactivity — add a weekly cron ping.

Upstash — Redis (Free)

10,000 commands/day free. Supports pub/sub. Serverless — you pay per command after free tier. At 60s scrape interval = ~1,440 scrapes/day × a few commands each = well under limit for MVP.

When to move to AWS

Move when: >500 users/day OR pub/sub hits Upstash limit OR Railway CPU/RAM consistently maxed. AWS migration is one env-var change per service — all the code stays identical.

Challenges — Status
All critical items resolved. Here's what changed and why.

✓ Docker healthchecks

pg_isready on all DBs. redis-cli ping on Redis. condition: service_healthy on all depends_on. Spring Boot now starts only after DB is truly ready.

✓ Single PostgreSQL (3 schemas)

Dropped 2 DB containers. One divtrack DB with auth, portfolio, market schemas. Each service sets currentSchema=X in connection URL. Flyway owns its own schema history per service. init-schemas.sql creates schemas on first boot.

✓ WebSocket fan-out implemented

4 new files written: SessionRegistry, PriceFanOutHandler, WebSocketConfig, RedisSubscriberConfig. Gateway is now a full WS server with Redis pub/sub fan-out. Sessions are thread-safe (ConcurrentHashMap + CopyOnWriteArraySet). Stale sessions cleaned on send error.

✓ JVM memory limits

JAVA_TOOL_OPTIONS: -Xmx384m -Xms128m -XX:+UseContainerSupport on all 4 services. Total: ~1.5GB. Use t3.small (2GB) on AWS or Railway's 512MB containers.

⚠ Yahoo Finance (still open)

Swap YahooFinanceScraper for Finnhub.io free API. The MarketDataProvider interface means: write FinnhubScraper implements MarketDataProvider, swap the Spring bean. Zero other changes.

⚠ Redis SPOF (partially mitigated)

Portfolio service now falls back to HTTP if Redis miss. Gateway's .retry() auto-resubscribes. Rate limiter fails open. For production: use Upstash (managed, replicated).
